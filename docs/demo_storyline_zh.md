**Vehicle NPI Platform 中文演示讲稿：从电池包热风险预警，到有证据的阶段评审**

适用版本：当前 Program Cockpit，包括 Models 门户、五智能体工作流图和可展开的 Lance 知识资产。建议演示时长：12–15 分钟。主角：新项目 `PACK-ATLAS-01`（Atlas Battery Pack）；历史参考项目：Orion 和 Vega。

这份讲稿中的引述可直接对客户讲。操作说明告诉演示者应点击哪里；文末的实现说明用于回答技术追问。所有工程数据都是为演示构造的合成数据。

**1. 开场：今天要解决什么业务问题？（1 分钟）**

操作：打开 `http://localhost:8100`，停留在 Program Cockpit。

> “假设我是 Atlas 电池包项目的项目经理。需求、设计和验证资料已经准备好，现在要召开阶段评审，决定这个项目能否继续放行。
>
> 我需要知道四件事：哪些需求有风险？测试是否支持当前设计？有没有验证或标准覆盖缺口？过去的项目有没有值得参考的经验？
>
> 今天我们用一个具体问题串起整个评审：Atlas 的热管理需求被传统机器学习模型标为高风险，同时测试规则发现它的裕量偏小。系统把这些信号与需求追溯、标准检查、历史资料放在一起，整理成供人审批的评审报告。”

演示主线：

```text
Atlas 热需求 → ML 风险 HIGH
                     ↓ 与另一条计算路径对照
设计值 103、目标 100 → 合成测试裕量 3% → MARGINAL
                     ↓ 联合检查
需求覆盖 80% + 成本验证缺口 + 必需标准覆盖缺口
                     ↓
规则计算 CONDITIONAL → 智能体解释与引用证据 → 人工决定
```

这里的“另一条计算路径”指测试公式与 ML 推理分开执行；两者使用同一组合成工程数据，不能称为两套独立实测证据。

**2. 先认清仪表板：每个组件解决什么问题？（2 分钟）**

操作：按顶部、左侧、中间、右侧的顺序指示各区域。

| 组件 | 业务用途 | 当前数据或行为 | 演示时的一句话 |
|---|---|---|---|
| 顶部 Program Cockpit / Models | 在项目评审与语言模型配置之间切换 | Models 用于注册、编辑、测试、激活 LLM 端点 | “这里配置负责解释的语言模型。” |
| 项目信息与阶段条 | 建立项目身份和生命周期背景 | 显示 Atlas、车型平台和需求至发布的阶段；来自项目源数据 | “今天关注的是进入阶段评审的 Atlas 项目。” |
| Requirements | 明确需要满足什么要求 | 展示 5 项需求、目标值、单位、优先级和状态 | “先定义目标，才能讨论设计是否充分。” |
| Design | 解释设计如何响应需求 | 展示设计 ID、关联需求、参数值、化学体系及版本 | “每个设计参数都有对应的需求。” |
| BOM | 展示设计背后的物料与供应商 | 零部件、供应商 ID、数量、单价和重量 | “成本和物料属性也能进入设计风险特征。” |
| Design risk | 排定值得优先检查的需求 | 传统 ML 输出的风险百分比、HIGH/MEDIUM/LOW 标签 | “热需求是本次评审的优先关注对象。” |
| Top features | 解释模型整体主要使用哪些特征 | 梯度提升模型的全局特征重要性 | “这个模型主要依靠哪些输入区分历史风险？” |
| Traceability matrix | 检查需求是否连到设计和测试 | 需求 → 设计 → 测试 → 判定；显示热测试 MARGINAL、成本项 gap | “不能只看分数，还要看验证链是否完整。” |
| Gate review 与 Run Gate Review | 发起本次多智能体评审 | 创建评审 ID，运行固定的五专家流程 | “现在把不同角度的证据组织成一次评审。” |
| Agent workflow 图 | 展示执行结构与进度 | Supervisor → 五个并行专家 → Code decision → Gate narrative | “并行收集证据，然后计算建议、撰写总结。” |
| 五个专家结果卡片与 EVD 标记 | 展示发现及其证据关联 | 各专家的文字摘要、对应证据记录 ID | “每个专家的发现都关联到一次工具读取记录。” |
| Gate review narrative | 给管理者一段可读的评审总结 | 语言模型基于专家发现及已计算的建议生成文字；失败时回退到模板 | “这是解释层，结构化建议另由代码确定。” |
| Knowledge base | 查阅历史设计、测试摘要和组件参考 | Lance 中的 10 个资产，支持查询、类型筛选和相似度排序 | “把历史资料放到当前风险的上下文中看。” |
| 资产详情弹窗 | 看清资料内容及用途 | 大图或文档正文、项目/实体 ID、复用说明、来源和许可 | “不仅知道找到了什么，还能打开看它具体说明什么。” |
| Gate decision | 记录人的最终判断 | APPROVED、APPROVED WITH CONDITIONS、REJECTED；审批人、理由、提交结果 | “系统提出建议，责任人作出最终决定。” |

BOM 展示的 `Mass (kg)` 应讲成“重量”，避免中文“质量”被误解为供应商质量评级。供应商质量评级来自后端参考数据，是 ML 的一个输入，当前 BOM 表没有单独展示该评级。

**3. 传统 ML 在哪里评分？这个百分比意味着什么？（3 分钟）**

操作：指向左侧 Design risk 的 `REQ-ATLAS-thermal` 行，再指向 Top features。

> “这里的百分比来自一个传统机器学习分类器：GradientBoostingClassifier，梯度提升分类模型。
>
> 它用 Orion、Vega 两个历史合成项目的需求、设计和测试标签进行训练。历史测试出现 FAIL 或 MARGINAL 的需求被标成风险类，PASS 被标成另一类。随后模型给 Atlas 的需求计算属于风险类的分数。
>
> 因此，这里的 HIGH 表示模型建议优先检查热需求。它不是大语言模型凭文字判断出的分数，也不是整份报告的准确率。”

评分过程可这样讲清楚：

```text
历史项目需求 + 设计 + BOM + 供应商评级
                     ↓ 组成 8 个特征
历史测试标签：FAIL / MARGINAL = 1；PASS = 0
                     ↓ 离线训练
GradientBoostingClassifier(random_state=42)
                     ↓ 对 Atlas 需求调用 predict_proba
risk_prob → 风险分档 → SQLite → Design risk 面板
```

| 输入特征 | 当前代码的含义 |
|---|---|
| `target_value` | 需求目标值 |
| `spec_value` | 对应设计参数值 |
| `margin` | `(spec_value - target_value) / target_value` |
| `bom_cost` | 关联 BOM 记录的单价，不是整包总成本 |
| `bom_mass` | 关联 BOM 记录的重量，不是整包总重量 |
| `supplier_quality` | 对应供应商的参考质量评级 |
| `is_thermal` | 是否为热相关需求 |
| `is_safety` | 是否为安全相关需求 |

当前特征构建按设计 ID 保留一条 BOM 记录，不进行完整的多零件聚合。讲解时不要把这个实现称为全量物料成本优化模型。

风险分档是固定规则：

| 风险分数 | 标签 |
|---|---|
| ≥ 0.66 | HIGH |
| ≥ 0.33 且 < 0.66 | MEDIUM |
| < 0.33 | LOW |

当前种子下，热需求分数接近 1，界面取整显示 **100% / HIGH**；其余已评分需求接近 0。推荐口播：

> “模型给出了很强的风险信号，值得我们继续查证。因为这是一个小规模合成数据模型，而且没有经过生产数据上的概率校准，所以这里显示的 100% 不能解释成现实中必然发生故障。”

Top features 当前约为：`spec_value` 0.51、`is_thermal` 0.44、`margin` 0.05，其余展示项接近 0。这些是**模型全局特征重要性**，不是逐条需求的 SHAP 解释，也不是因果证明。

当前评分实现复用了一套要求存在测试计划和测试结果的特征构建逻辑，所以 Atlas 有 5 项需求，但只有 4 项评分；成本需求没有测试计划而被跳过。成本项没有分数意味着“未评分”，不能解读为“风险为零”。展示的是设计风险预警的业务用途，当前实现还不是完全在测试前运行的预测流程；Atlas 的测试标签不会进入 `predict_proba` 的 8 个输入特征。

操作：可短暂打开 Models，再返回 Program Cockpit。

> “Models 门户控制五个专家和总结使用哪个语言模型。更换这个端点不会重训左边的传统 ML，也不会改变固定的风险阈值或阶段建议规则。”

**4. 从高风险追到验证证据：为什么热需求是 MARGINAL？（1–2 分钟）**

操作：切到 Design 看热设计值，再指向 Traceability matrix 的 thermal 行与 cost 行。

> “风险分数提醒我们看哪里。接着看验证链：热需求的目标值是 100，设计值是 103。演示中的确定性测试台根据设计参数计算模拟测量值，得到 3% 的裕量。
>
> 规则要求裕量至少 10% 才是 PASS；在 0 到 10% 之间是 MARGINAL。因此热测试被标成边缘状态。它没有触发 FAIL，但不满足本演示的充分裕量要求。”

本例计算：`(103 - 100) / 100 = 0.03`。

| 演示测试裕量 | 判定 |
|---|---|
| ≥ 10% | PASS |
| ≥ 0 且 < 10% | MARGINAL |
| < 0 | FAIL |

> “再看成本需求：有需求和设计，但没有测试计划，所以出现 gap。总共五项需求，四项连接了设计与测试计划，追溯覆盖率就是 80%。”

这里的 80% 是**链接覆盖率**，不是测试通过率；Atlas 当前 4 个测试结果为 3 个 PASS、1 个 MARGINAL。测试数值是从设计值计算出的合成结果，不是读取真实实验室设备；这些简化阈值也不是对真实电池法规判定方法的实现。

**5. 打开历史资料：Lance 知识库如何帮助解释风险？（2 分钟）**

操作：右侧保留默认查询 `thermal runaway containment design`，点击 Orion 热设计的 **Open asset & details**。关闭弹窗后打开 Orion 热测试报告；如需展示照片，选择 ComponentPhoto 后点击 Search。

> “当前风险是热管理，我们希望知道以前的项目留下了什么经验。知识库返回了 Orion 的热设计示意图和测试报告摘要。
>
> 打开图片，可以看到模块、隔热屏障与冷却路径的示意。打开报告，可以看到历史合成案例的 FAIL 结论和问题描述。两项资料都带有项目和关联需求 ID，所以我们能理解它们为什么与当前评审有关。
>
> 这些材料用于帮助工程师理解风险和提出后续检查方向；历史设计不能直接证明新项目已经通过验证。”

Lance 把图片/文档字节、标题、说明、向量和关联实体放在同一个数据集中。图片是可展开的真实文件内容，热图为明确标注的合成示意图，组件照片为有署名和许可的 BMW i3 参考照片，不是 Atlas 或 Vega 的实物照片。

要区别三个容易混淆的数值：

| 界面数值 | 回答的问题 | 不能解释为 |
|---|---|---|
| Design risk 的百分比 | 模型对该需求风险类别的输出有多高？ | 真实故障概率的保证，或报告可信度 |
| 80% coverage | 有多少需求连接了设计和测试计划？ | 80% 测试通过，或 80% 合规 |
| Knowledge base 的 Similarity | 资产说明与查询在向量空间中有多接近？ | 图片正确率、证据强度或工程置信度 |

当前检索根据资产的**文字说明**生成向量，优先尝试本地缓存的 MiniLM，否则使用确定性 token-hash 向量。排序用余弦相似度。当前流程没有视觉模型对图片做热传播分析，也没有用 OCR 自动理解报告。大图供人查看；智能体没有通过视觉消息读取图片。

**6. 点击 Run Gate Review：五个智能体怎样协作？（3 分钟）**

操作：点击 **Run Gate Review**，指向工作流图。未配置 LLM 时模板执行很快，可以在完成后沿着保留的图继续解释。

> “Supervisor 按固定流程派出五个专家。它们读取的是面板背后的同一组工程数据和结果，不是对界面截图做分析。
>
> 每个专家收集自己的数据切片、记录工具读取的证据信息，然后给出摘要。五个角度合起来，才能回答‘为什么建议有条件推进’。”

| 专家 | 对应面板/后台数据 | 读取与证据记录 | 本次应关注的发现 |
|---|---|---|---|
| Coverage | Requirements、Design、Traceability matrix | 需求—设计—测试关系矩阵；计算覆盖率，记录矩阵读取证据 | 4/5 覆盖、成本需求存在 gap |
| Test Verdict | Traceability matrix 背后的测试结果 | SQLite 的测试结果；记录 `get_test_results` 证据 | 3 PASS、1 MARGINAL，热测试需要关注 |
| Compliance | 源测试计划中的标准字段；结果在专家卡片展示 | 检查代码配置的标准列表，记录 required/missing 标准 | 当前 UN38.3、GB 38031、IEC 62660 三项都未被结构化测试计划覆盖 |
| Design Risk | Design risk、Top features | 读取预先计算的评分与全局重要性，分别记录证据 | 热需求 HIGH；解释模型主要使用的特征 |
| Knowledge Reuse | Knowledge base 与 ontology | 固定热主题查询取前 3 项；记录检索及顶层资产类型说明 | 找到 Orion 等项目的热相关历史资料并引用资产 ID |

BOM、设计和供应商数据在准备阶段参与传统 ML 特征构建；Design Risk 专家运行时读取已保存评分，**不会现场重训模型或重新遍历全部 BOM**。阶段条负责提供生命周期背景；Models 配置负责语言模型连接；人工审批是评审之后的动作，它们不是五个专家逐一检索的证据面板。

知识专家当前使用固定热主题查询，不会自动跟随用户在右侧输入的新搜索词，也没有自主生成搜索策略。五专家属于预定义编排，并非模型自由规划的智能体网络。工作流图通过 SSE 更新状态；后端在并行任务收齐后按固定顺序发送完成结果，因此卡片可能一起完成。图中的 8/8 表示 8 个工作流节点完成，不代表存在 8 个专家。

**7. 系统如何得出 CONDITIONAL，并形成可信任的评审材料？（2 分钟）**

操作：指向 CONDITIONAL 标签、五个专家卡片、EVD 标记和 Gate review narrative。

> “收齐专家发现之后，Supervisor 直接用覆盖率、测试判定和缺失标准计算阶段建议。这个结构化建议没有经过大语言模型投票。
>
> Atlas 没有 FAIL 测试，覆盖率也没有低于 60%，所以不触发 FAIL。但是热测试 MARGINAL、成本覆盖有缺口，而且必需标准覆盖不足，因此规则给出 CONDITIONAL。
>
> 最后，语言模型接收这个已确定的建议和专家发现，写成管理者容易阅读的总结。语言模型不可用时，确定性模板仍然能把流程走完。”

当前实际决策顺序：

```text
任一测试 FAIL，或者覆盖率 < 60%
    → FAIL
否则，存在 MARGINAL、覆盖缺口、缺失标准中的任一项
    → CONDITIONAL
否则
    → PASS
```

**ML 分数和知识库相似度没有直接进入 `decide()`。** ML 提供优先级和解释背景；历史知识提供复用背景。结构化阶段建议由测试、覆盖和标准规则决定。即使更换 LLM，计算得到的建议也不变；自然语言措辞可能变化。

可将“可信任”讲为四个具体机制：

| 机制 | 当前实现带来的价值 | 实现边界 |
|---|---|---|
| 同一数据基础 | 界面与专家读取共同的源数据、SQLite 结果和 Lance 资产，能对照核查 | 不是五个专家各自独立采集的外部事实 |
| 显式计算规则 | 测试判定、覆盖、风险分档和阶段建议有可查代码 | 规则是演示规则，不等于完整工程认证 |
| 工具读取留痕 | SQLite 证据表记录 review ID、工具、查询、worker、数据版本标记、payload 的 SHA-256 | 当前仅保存摘要哈希与元数据，没有持久化完整 payload 快照或逐句事实核验 |
| 人工最终审批 | 审批结果、审批人、理由写入运行数据库 | 审批人字段是用户填写的名字，不是经过身份认证的电子签名 |

EVD 标记目前是显示用的证据 ID，不是可点击的完整审计浏览器。SHA-256 有助于比较数据内容，不能单独证明输入是真实的或记录绝不可能被修改。当前 `data_version` 是固定的 `src-v1`，不是自动计算的全数据集版本。

使用 LLM 时，目前没有对其每句话做自动事实校验。因此应说“报告具备结构化事实依据和可追溯关联”，不要说“已消除幻觉”或“每句话都已验证”。最终报告保存在 `gate_reviews` 中；专家摘要在本次流与界面中展示，尚未提供一套完整、独立持久化的逐专家报告回放系统。

**8. 让人作出最终决定（1 分钟）**

操作：在 Gate decision 中选择 **APPROVED WITH CONDITIONS**，填写审批人，例如 `演示项目经理`，填写理由：

> `热裕量偏小；推进下一阶段前需完成隔热设计复核与复测、补齐成本验证计划及标准覆盖。`

点击 **Submit decision**。

> “系统给出的是 CONDITIONAL 建议。作为项目负责人，我选择附条件批准，并记录需要完成的事项和我的理由。这样就把风险发现、解释材料和人的最终判断连在同一次评审上。”

当前审批会保存到 SQLite 的 `annotations` 和 `gate_reviews`。注意两个界面行为：所有三种审批选项提交后，当前代码都会把这条评审记录的 `state` 写成 `RELEASED`；它不代表真实产品一定已获发布许可。顶部阶段条读取只读项目源数据，不会因为本次审批同步变化。演示时应以审批结果区域显示的 `decision` 为准，不要承诺完整的发布流程或整改闭环已经实现。

**9. 收尾：客户应记住的业务价值（30 秒）**

> “今天我们把一个热风险问题沿着证据链走完了：传统 ML 先给出优先检查的信号，测试规则说明当前裕量，追溯矩阵发现验证缺口，标准检查补充覆盖情况，知识库提供历史参考。
>
> 五个智能体把这些数据组织成评审材料，代码给出阶段建议，负责人作出最终决定。这个演示的价值，是让团队更快地知道该关注什么、依据在哪里、下一步该由谁判断。”

**10. 演示者速查：常见追问的回答**

| 客户提问 | 推荐回答 |
|---|---|
| “100% 是模型的准确率吗？” | “不是，是该需求的风险类输出经过百分比显示；模型没有生产概率校准，不能把它当成真实故障保证。” |
| “是不是大模型给热需求打高分？” | “不是。梯度提升模型计算风险；LLM 负责说明已有评分和评审结果。” |
| “每次点评审都会训练模型吗？” | “不会。准备脚本完成训练和评分；评审读取已有结果。” |
| “为什么成本需求没有分数？” | “当前特征构建只保留有测试计划和结果的需求，成本项被排除；覆盖专家会把这个缺口指出来。” |
| “ML 高风险一定导致 CONDITIONAL 吗？” | “不会直接导致。当前决策函数检查测试判定、追溯覆盖和标准缺口；ML 是补充的风险信号。” |
| “标准没有覆盖，就说明产品违反法规吗？” | “不能这样判断。当前只是对测试计划的 standard 字段做固定列表匹配，不能替代合规认证。” |
| “图片是 AI 识别后判断有风险的吗？” | “不是。当前检索基于文字说明，图片供人查看；没有视觉模型推理。” |
| “断网还能演示吗？” | “数据、模型和 Lance 资产准备好后可以离线运行，LLM 不可用会回退到模板。” |
| “相同数据每次完全一样吗？” | “核心评分、测试判定和阶段建议可重复；LLM 文字可能不同，运行级 review/evidence ID 和时间也会变化。” |
| “证据卡能证明每句话都正确吗？” | “它提供与工具读取的关联；当前没有逐句核验和完整 payload 快照，需要结合原始数据复核。” |

额外数据注意：当前 Lance 热报告示例正文写有 `IEC 62660`，而源测试计划的热测试标准字段为 `ISO-12405`。Compliance 专家以结构化测试计划为准，因此仍报告三项必需标准未覆盖。不能拿示例报告文字声称该标准已满足；若客户追问，应说明这暴露了演示资料之间尚未完成的一致性校验。
